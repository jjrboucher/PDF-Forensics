Before You Begin

Open a terminal in the folder containing lab04_images.pdf. Also open the file in your PDF viewer so you can compare what the viewer shows against what the tools reveal. You will need a notepad for recording object numbers, BBox values, matrix values, and DPI calculations. Keep the DPI formula handy: effective_dpi = pixel_width × 72 / display_width_pts.

🔬 Page 1 — BBOX_CROP

ℹ️
What this module is about

A PDF can display only part of an image while still storing the whole thing. Four techniques do this: cropping with a Form BBox, stacking one image over another, pushing an image off the page, and mixing images at different resolutions. In every case the hidden pixels are still in the file — and mutool extract pulls them out exactly as stored, bypassing all of these display tricks. Each page below is one technique; work them in order.

The technique: a Form XObject has a /BBox (bounding box) that acts like a window. If the image drawn inside the form is larger than that window, only the part inside the window shows — the rest is clipped away in every viewer, but still fully present in the file. Here the window is 200×150 and the image is 400×300, so three-quarters of it is hidden.

Step 1 — Find the Form XObject

Open the file and draw the object tree; look on page 1 for an XObject whose subtype is /Form:

peepdf session
peepdf -i lab04_images.pdf
pdf> tree
Terminal — pdf> tree (page 1 branch)
pdf> tree /Catalog (1) /Pages (3) /Page (13) /XObject /Form (21) <- the clipping window /Image (22) <- the full image inside it ... pages 2-4 ...

👆 Page 1 draws Form object 21, and inside that form is Image object 22. The form is the window; the image is what it clips.

Step 2 — Read the form’s BBox and the image’s real size

peepdf session
pdf> object 21
pdf> object 22
Terminal — the window vs the image
pdf> object 21 (the Form XObject) << /Type /XObject /Subtype /Form /BBox [0 0 200 150] <- window is only 200 x 150 /Resources << /XObject << /ImA 22 0 R >> >> >> (its stream draws: q 400 0 0 300 0 0 cm /ImA Do Q) pdf> object 22 (the Image) << /Type /XObject /Subtype /Image /Width 400 /Height 300 <- real image is 400 x 300 /Filter /DCTDecode >>

👆 The window (/BBox) is 200×150, but the image is drawn at 400×300 (the 400 0 0 300 scale in the form’s cm matrix). The window shows only the bottom-left quarter; the other three quarters are clipped.

🧮
Calculate how much is hidden

Visible area = 200×150 = 30,000. Full image area (as drawn) = 400×300 = 120,000. Visible fraction = 30,000 / 120,000 = 25%, so 75% of the image is hidden.

Step 3 — Extract the full image to see what was hidden

extract and view
mutool extract lab04_images.pdf
# then open the extracted image for object 22 (img-0022.jpg)
Terminal — the hidden content revealed
mutool extract lab04_images.pdf extracting image img-0022.jpg ... # opening img-0022.jpg shows the FULL image, including the # three-quarters the viewer clipped away, which reads: ORIGINAL RECEIPT DATA Fee billed: $8,500.00 Not $48,500.00

👆 The hidden three-quarters of the image states the original fee was $8,500.00, not $48,500.00 — content the document hid behind the BBox window but never removed.

✅
What to record

Form (obj 21) BBox 200×150 clips Image (obj 22) drawn at 400×300 — 75% hidden. The extracted full image reveals the original $8,500 fee. Finding class: BBOX_CROP.

🔬 Page 2 — OVERLAP

The technique: two images occupy the same spot on the page. PDF draws in order, so whichever image is drawn second lands on top and hides the one drawn first. The hidden “back” image is still in the file — you just have to read the draw order to know it is there, then extract it.

Step 1 — Read the page-2 content stream (the draw order)

Decode page 2’s content stream (object 16) and read the two image-drawing operations in order:

decode page 2 content
qpdf --show-object=16 --filtered-stream-data lab04_images.pdf
Terminal — page 2 draw order
qpdf --show-object=16 --filtered-stream-data lab04_images.pdf BT /F2 12 Tf 1 0 0 1 72 730 Tm (Figure 2 ...) Tj ET q 200 0 0 150 100 380 cm /ImC Do Q <- drawn FIRST (back) q 300 0 0 200 50 340 cm /ImB Do Q <- drawn SECOND (covers ImC)

👆 /ImC is drawn first, then /ImB is drawn over roughly the same area — so ImC is the hidden back image and ImB is the visible cover. The rule: the image drawn earlier in the stream is the one underneath.

Step 2 — Map the names to object numbers

The page’s /Resources tells you which object each name points to:

peepdf session
pdf> object 15   (the page 2 object, to read its /Resources)
Terminal — resolving the image names
pdf> object 15 ... /XObject << /ImB 23 0 R /ImC 24 0 R >> ...

👆 So the hidden back image /ImC is object 24, and the visible cover /ImB is object 23.

Step 3 — Extract and view the hidden image

extract
mutool extract lab04_images.pdf
# open the image for object 24 (img-0024.jpg) -- the hidden back image
Terminal — the concealed document
# img-0024.jpg (the back image /ImC) reads: HIDDEN DOCUMENT Original scope: $8,500

👆 The concealed back image is a document stating the original scope was $8,500 — hidden under the “site photo” cover.

✅
What to record

Two images overlap; draw order shows ImC (obj 24) is drawn first and covered by ImB (obj 23). The hidden back image reveals the original $8,500 scope. Finding class: OVERLAP.

🔬 Page 3 — OFFPAGE

The technique: an image is positioned so that part of it sits outside the page boundary. The page only shows what falls within its /MediaBox; anything placed at a negative coordinate hangs off the edge, invisible but still stored. Here an image is pushed 80 points off the left edge.

Step 1 — Read the page-3 content stream

decode page 3 content
qpdf --show-object=18 --filtered-stream-data lab04_images.pdf
Terminal — page 3 image placement
qpdf --show-object=18 --filtered-stream-data lab04_images.pdf BT /F2 12 Tf 1 0 0 1 72 730 Tm (Figure 3 ...) Tj ET q 300 0 0 200 -80 400 cm /ImD Do Q <- x = -80 (off the left edge)

👆 The cm matrix is 300 0 0 200 -80 400: the image is 300 wide, placed at x = −80. A negative x means its left 80 points sit off the page, to the left of the /MediaBox origin.

Step 2 — Confirm against the page bounds

peepdf session
pdf> object 17   (the page 3 object, to read its /MediaBox)
Terminal — the page boundary
pdf> object 17 ... /MediaBox [0 0 612 792] ...

👆 The page starts at x = 0, but the image starts at x = −80 — so an 80-point-wide strip of the image hangs off the left edge and never renders. That strip is where the hidden content lives.

Step 3 — Extract to read the off-page strip

extract
mutool extract lab04_images.pdf
# open the image for object 25 (img-0025.jpg) -- includes the off-page strip
Terminal — the off-page content
# img-0025.jpg (object 25) full image includes the clipped left strip: ORIGINAL TERMS Fee: $8,500

👆 The off-page portion reads “ORIGINAL TERMS / Fee: $8,500” — the original terms, hidden by pushing them past the page edge.

✅
What to record

Image (obj 25) placed at x = −80 on a page with MediaBox origin x = 0 — 80 points hang off the left edge. The extracted image reveals the original $8,500 terms. Finding class: OFFPAGE.

🔬 Page 4 — DPI_ANOMALY

The technique: in a genuinely scanned document every image shares roughly the same resolution (dots per inch). When one image on a “scanned” page has a very different effective DPI, it was inserted from another source — a screenshot pasted among scans, for example. You detect this by comparing each image’s pixel dimensions against its display size.

🧮
The DPI formula

effective DPI = (pixel width ÷ display width in points) × 72. (There are 72 points per inch, so dividing pixels by points and multiplying by 72 gives pixels-per-inch.)

Step 1 — Read the page-4 content stream for the display sizes

decode page 4 content
qpdf --show-object=20 --filtered-stream-data lab04_images.pdf
Terminal — page 4 display sizes
qpdf --show-object=20 --filtered-stream-data lab04_images.pdf BT /F2 12 Tf 1 0 0 1 72 730 Tm (Figure 4 ...) Tj ET q 150 0 0 100 72 560 cm /ImE Do Q <- ImE displayed 150 pts wide q 144 0 0 96 72 430 cm /ImF Do Q <- ImF displayed 144 pts wide

Step 2 — Read each image’s pixel dimensions

peepdf session
pdf> object 26
pdf> object 27
Terminal — pixel dimensions
pdf> object 26 (/ImE) << /Subtype /Image /Width 150 /Height 100 ... >> pdf> object 27 (/ImF) << /Subtype /Image /Width 600 /Height 400 ... >>
🧮
Compare the two DPIs

ImE: 150 px ÷ 150 pt × 72 = 72 DPI — screen resolution, i.e. a screenshot.
ImF: 600 px ÷ 144 pt × 72 = 300 DPI — typical scanner resolution.

A 72-DPI image sitting among 300-DPI scans did not come from the scanner. It was captured on-screen and pasted in.

✅
What to record

ImE (obj 26) = 72 DPI (screenshot); ImF (obj 27) = 300 DPI (scan). The resolution mismatch shows ImE was inserted from a different source. Finding class: DPI_ANOMALY.

📝 Knowledge Check Preparation

Q1: /BBox [0 0 200 150], image placement '400 0 0 300 0 0 cm'. What percentage is hidden?

75% is hidden.

The /BBox is the visible window: 200×150 = 30,000 square units. The cm matrix 400 0 0 300 0 0 draws the image at 400×300 = 120,000 square units. Visible fraction = 30,000 / 120,000 = 25%, so 100% − 25% = 75% is clipped away.

Why it matters: every one of those hidden pixels is still in the file. Extracting object 22 reveals the clipped portion, which states the original fee was $8,500 — the content the BBox window concealed.

Q2: When two images overlap, which is considered the 'back' (hidden) image?

The image drawn first in the content stream is the back (hidden) image.

PDF paints in stream order, like stacking sheets of paper: each drawing operation lands on top of whatever is already there. So when two images cover the same area, the one whose Do operator appears earlier ends up underneath, and the later one hides it. On page 2, /ImC is drawn before /ImB, so ImC (object 24) is the hidden back image and ImB is the visible cover.

How to prove it: read the content stream to establish draw order, map the names to objects via the page’s /Resources, then extract the back image and view what it was hiding (here, a document showing the original $8,500 scope).

Q3: Image at x=-80 pts on a page with MediaBox [0 0 612 792]. What does OFFPAGE mean?

Part of the image sits outside the page boundary, so it never renders — but it is still stored in the file.

The page’s visible area is its /MediaBox, which starts at x = 0. Placing an image at x = −80 means its left 80 points hang off the left edge, beyond the page. A viewer clips anything outside the MediaBox, so that strip is invisible on screen — yet the complete image is embedded and comes out whole when you extract it.

Here: the off-page strip of object 25 reads “ORIGINAL TERMS / Fee: $8,500” — the original terms hidden by pushing them past the page edge. Finding class: OFFPAGE.

Q4: Image: 150 pixels wide, displayed at 150 points wide. What is the effective DPI?

72 DPI.

Effective DPI = (pixel width ÷ display width in points) × 72, because there are 72 points per inch. Here: (150 px ÷ 150 pt) × 72 = 1 × 72 = 72 DPI — exactly screen resolution, the hallmark of a screenshot.

Why it is an anomaly: the other image on the same “scanned” page computes to (600 px ÷ 144 pt) × 72 = 300 DPI, a normal scanner resolution. A 72-DPI image mixed in with 300-DPI scans did not come off the scanner — it was captured on-screen and pasted in. A uniform scan set should show uniform DPI.

Q5: Which command extracts the full uncropped image from a BBOX_CROP finding?

mutool extract lab04_images.pdf

mutool extract writes every embedded image to its own file using the raw stored pixel data — it ignores the Form /BBox window, the page /MediaBox, draw order, and every other display-level instruction. That is the whole point: those tricks only affect what a viewer shows, not what is stored. The extracted file for object 22 contains the full 400×300 image, including the 75% the BBox clipped.

Good practice: run it in a clean working folder so the extracted img-00NN.jpg files land in a known place, then open the one whose number matches the clipped image’s object number.
