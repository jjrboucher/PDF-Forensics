Extract and interpret EXIF metadata from three embedded images, then locate and read the reviewer annotations left in the document.

Scenario

You have received a three-page site inspection report. The submitting party claims all photographs were captured at the Callahan property in Portland, OR using the office Canon scanner on 10–15 April 2025. Your task is to verify or refute this claim using EXIF metadata analysis.

ℹ️
Before You Begin

Open a terminal in the folder containing lab06_exif_comments.pdf. You will first extract images to separate files, then run ExifTool on each. Prepare a table in your notes with columns: Image filename | Page | Make | Model | DateTimeOriginal | GPS present? | GPS location | Anomaly?

🔬 Exercise 1 — Extract Images and Run ExifTool

Goal: pull the three embedded photographs out of the PDF and read the EXIF metadata buried inside each one. EXIF is the data a camera or scanner writes into an image — the device make and model, the date and time, and sometimes GPS coordinates. The document claims all three images were produced by the same office scanner; the EXIF will let you test that claim.

ℹ️
Why extract the image instead of reading the PDF?

EXIF lives inside the image file, not in the PDF’s own metadata. A PDF viewer never shows it. You have to pull the raw image out with mutool extract and then run exiftool on the extracted file to see what the camera recorded.

Step 1 — Extract the embedded images

🪟 Windows
🐧 Linux / macOS
PowerShell
mutool extract lab06_exif_comments.pdf
dir img-*
Bash
mutool extract lab06_exif_comments.pdf
ls img-*
Terminal — mutool extract lab06_exif_comments.pdf
mutool extract lab06_exif_comments.pdf extracting image img-0019.jpg extracting image img-0020.jpg extracting image img-0021.jpg ls img-* img-0019.jpg img-0020.jpg img-0021.jpg

👆 Three images come out, named after their PDF object numbers: img-0019 (page 1), img-0020 (page 2), img-0021 (page 3). The exact numbers and extension can vary slightly by mutool version — what matters is that you get three image files, one per page.

Step 2 — Run ExifTool on all three

Run ExifTool on every extracted image at once and save the output to a text file so you can review it carefully:

🪟 Windows
🐧 Linux / macOS
PowerShell
exiftool img-*.jpg | Tee-Object exif_report.txt
Bash
exiftool img-*.jpg | tee exif_report.txt
Terminal — exiftool img-*.jpg
exiftool img-*.jpg ======== img-0019.jpg Make : Canon Camera Model Name : imageRUNNER 2630 Date/Time Original: 2025:04:12 14:22:35 (no GPS tags) ======== img-0020.jpg Make : SAMSUNG Camera Model Name : SM-G991B Date/Time Original: 2025:04:08 09:14:07 GPS Latitude : 36 deg 10' 11.64" N GPS Longitude : 115 deg 8' 23.28" W ======== img-0021.jpg Make : FUJIFILM Camera Model Name : X-T5 Date/Time Original: 2025:04:14 16:45:22 (no GPS tags)

👆 Already the story falls apart. The three “scanned” images come from three different devices — a Canon scanner, a Samsung phone, and a Fujifilm camera — and the Samsung image carries GPS coordinates a scanner would never record. You will tabulate this in Exercise 2 and decode the GPS in Exercise 3.

✅
What to record from Exercise 1

Three images, three different Make/Model values (Canon / SAMSUNG / FUJIFILM), and GPS tags present only on img-0020.jpg. Keep exif_report.txt for your notes.

🔎
The finding, stated for a report

The document represents all three photographs as output from a single office scanner. EXIF shows three distinct capture devices (a Canon scanner, a Samsung SM-G991B smartphone, and a Fujifilm X-T5 camera), and the smartphone image carries GPS coordinates placing it in Las Vegas, Nevada — not the Portland property. The images therefore did not originate as a uniform scan set as claimed.

ℹ️
How to identify device types from Make/Model

Canon imageRUNNER — office scanner. Consistent with the claim.
SAMSUNG SM-GXXXXX — Samsung Galaxy smartphone. Not a scanner.
FUJIFILM X-T5 — mirrorless digital camera. Not a scanner.

Any device other than a scanner in a supposedly scanned document is an anomaly requiring explanation. Multiple different devices across pages of the same scan is a further anomaly — a single scan run would produce uniform EXIF across all pages.

🔬 Exercise 3 — Decode the GPS Coordinates from img-0020.jpg

Goal: turn the Samsung image’s GPS tags into a real-world location. ExifTool reports GPS in degrees/minutes/seconds; you will convert that to decimal degrees and look the point up on a map. This is the exact workflow you use any time an exhibit contains GPS data.

Step 1 — Read the raw (decimal) GPS values

The # suffix on each tag tells ExifTool to print the raw numeric value instead of the formatted degrees/minutes/seconds, which gives you decimal degrees directly:

🪟 Windows
🐧 Linux / macOS
PowerShell
exiftool -GPSLatitude# -GPSLongitude# img-0020.jpg
Bash
exiftool -GPSLatitude# -GPSLongitude# img-0020.jpg
Terminal — GPS in decimal degrees
exiftool -GPSLatitude# -GPSLongitude# img-0020.jpg GPS Latitude : 36.1699 GPS Longitude : -115.1398

👆 Latitude 36.1699, longitude −115.1398. A negative longitude means West; a positive latitude means North. (If you only have the degrees/minutes/seconds form — 36°10′11.64″N, 115°8′23.28″W — convert with decimal = degrees + minutes/60 + seconds/3600, then make longitude negative because it is West.)

Step 2 — Look the coordinates up

Paste 36.1699, -115.1398 into any mapping service, or build a maps link:

look up the point
# Opens the location in a browser map:
# https://www.google.com/maps?q=36.1699,-115.1398
📍
Result

36.1699, -115.1398 resolves to Las Vegas, Nevada, USA — roughly 1,600 km from the Portland, Oregon property the document claims. A genuine on-site scan of the Portland property could not carry Las Vegas GPS. This photo was taken somewhere else and inserted into the report.

✅
What to record from Exercise 3

Q2 answer: GPS = 36.1699°N, 115.1398°W = Las Vegas, Nevada — inconsistent with the claimed Portland origin. Quote both the decimal coordinates and the resolved city in your report.

🔬 Exercise 4 — Extract and Read the Reviewer Annotations

Goal: read the comments people left inside the PDF. Annotations (sticky notes, highlights, text comments) each record an author in the /T key and the comment text in /Contents. They often capture a reviewer’s own doubts about a document — which can corroborate your technical findings.

Step 1 — Find the annotation objects

peepdf session
peepdf -i lab06_exif_comments.pdf
pdf> search /Annot
Terminal — pdf> search /Annot
pdf> search /Annot [22, 23, 24]

👆 Three annotation objects: 22, 23, 24 — one per page.

Step 2 — Read each annotation’s author and text

peepdf session
pdf> object 22
pdf> object 23
pdf> object 24
pdf> exit
Terminal — reading the three reviewer notes
pdf> object 22 << /Type /Annot /Subtype /Text /T (D. Chen) /Contents (Scan A looks authentic - Canon office scanner EXIF matches equipment log.) >> pdf> object 23 << /Type /Annot /Subtype /Text /T (M. Patel (QA)) /Contents (CHECK: Photo B EXIF is a Samsung smartphone and GPS resolves to Las Vegas, not the Portland property.) >> pdf> object 24 << /Type /Annot /Subtype /Text /T (M. Patel (QA)) /Contents (INCONSISTENT: Photo C is a Fujifilm camera, not the office scanner.) >>

👆 The reviewer M. Patel (QA) already flagged exactly what your EXIF analysis found — the Samsung/Las Vegas anomaly and the Fujifilm device mismatch. These internal comments corroborate your technical findings and name who noticed.

ℹ️
How much weight does the /T author carry?

/T is just a text string that any tool can set or change — it is claimed authorship, not proof of identity. Treat an annotation author as a lead to corroborate (against the reviewer’s account, login records, or the annotation’s own /CreationDate), not as established fact.

✅
What to record from Exercise 4

Three /Text annotations (objects 22–24). Authors: D. Chen (p1) and M. Patel (QA) (p2, p3). The QA comments independently flag the Samsung/Las Vegas and Fujifilm anomalies. Note that /T authorship is editable and must be corroborated.

📝 Knowledge Check Preparation

Q1: EXIF Make='SAMSUNG', Model='SM-G991B'. Document claims all images are scanned. What is the significance?

The image was taken with a Samsung Galaxy smartphone, not produced by the office scanner the document claims.

SM-G991B is the model number of a Samsung Galaxy S21. A document that presents its images as uniform output from a Canon imageRUNNER 2630 office scanner cannot also contain a phone photo — the capture device is physically different. This is a device-mismatch anomaly: the EXIF Make/Model contradicts the stated source of the image.

How to state it: “EXIF on img-0020.jpg reports Make=SAMSUNG, Model=SM-G991B (a smartphone), inconsistent with the document’s claim that all images were produced by a Canon office scanner.”

Q2: ExifTool shows GPSLatitude: 36.1699, GPSLongitude: -115.1398. Document claims Portland. What should you do?

The photo was taken in Las Vegas, Nevada — not at the Portland property the document claims.

Positive latitude = North, negative longitude = West, so 36.1699, -115.1398 is 36.1699°N, 115.1398°W. Looked up on a map that point is Las Vegas, Nevada — roughly 1,600 km from Portland, Oregon.

Why it is decisive: a genuine on-site scan or photo of the Portland property could not carry Las Vegas GPS. The coordinates place the image’s origin somewhere it could not have been if the document’s account were true. Quote both the decimal coordinates and the resolved city in the report, and note that an office scanner would not embed GPS at all — only a GPS-equipped device (like the Samsung phone) would.

Q3: Which ExifTool command extracts GPS coordinates in decimal degree format from all JPEGs?

Add the # suffix to the GPS tags so ExifTool prints the raw decimal value:

exiftool -GPSLatitude# -GPSLongitude# img-*.jpg

Without the #, ExifTool formats GPS as degrees/minutes/seconds (e.g. 36 deg 10' 11.64" N), which you would then have to convert by hand. The # suffix on any tag tells ExifTool to output the underlying numeric value, giving you 36.1699 and -115.1398 directly — ready to paste into a map. Running it against img-*.jpg processes every extracted image at once.

Q4: Annotation has /T (D. Chen). What does /T represent and how reliable is it?

/T is the annotation’s title/author field — the name shown as the comment’s author. It is only as reliable as the claim behind it.

In the annotation dictionary, /T holds the author string and /Contents holds the comment text. Here /T (D. Chen) means the note is attributed to D. Chen. But /T is an ordinary editable string: it reflects whatever name was set in the tool’s preferences (or edited afterward), not a verified identity. So treat it as claimed authorship — a useful lead to corroborate against the reviewer’s own account, login/audit records, or the annotation’s /CreationDate — never as proof that a specific person wrote it.

Q5: When using mutool extract, where are files saved?

In the current working directory — the folder your terminal is in when you run the command.

mutool extract lab06_exif_comments.pdf writes each embedded image as a separate file (here img-0019.jpg, img-0020.jpg, img-0021.jpg) into the folder you are currently in — not next to the PDF if that is elsewhere, and not into a subfolder. The filenames are based on each image’s PDF object number, and the exact number/extension can vary by mutool version.

Practical tip: make a fresh working folder, copy the lab PDF into it, and cd there before extracting — so the extracted images land in a known place and do not clutter your Downloads folder.
