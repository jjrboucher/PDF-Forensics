Incremental Updates: The Edit Record

🔄 1. How Incremental Updates Work

When a PDF editor saves using incremental update mode, it appends three elements after the existing %%EOF:

  1. New/modified objects — only the objects that changed
  2. A new xref table — mapping new/modified objects to their byte offsets
  3. A new trailer — with a /Prev entry pointing back to the previous xref
Byte 0 %PDF-1.7 ← Header ... VERSION 1 BODY 1143 %%EOF ← End of Version 1 1144 VERSION 2 BODY ← New objects appended ... trailer << /Prev 809 >> ← /Prev links back 1911 %%EOF ← End of Version 2 2690 %%EOF ← End of Version 3 (current)

Key insight: the original bytes are never modified. Version 1 content is still intact, between bytes 0 and 1143. You can extract it.

🔢 2. Counting %%EOF Markers

%%EOF CountMeaningForensic Note
1Original, single-pass creationNo recorded post-creation edits in file structure
2One incremental updateCheck for linearisation first — linearised files have two %%EOF by specification
3+Multiple editsEach additional %%EOF = one more save — extract prior versions
⚠️
Linearised PDFs

Web-optimised ('linearised') PDFs contain two %%EOF markers by specification — this is not an edit indicator. Check the first 1024 bytes for the /Linearized key before interpreting a two-%%EOF count as an edit.

✂️ 3. Extracting Prior Versions

To extract Version 1 from a three-version file, copy all bytes from offset 0 through the first %%EOF. To extract Version 2, copy from offset 0 through the second %%EOF. Each extracted slice is a complete, valid PDF that can be opened in any viewer.

Python (both platforms) — extract all prior versions
python3 -c "
d = open('lab03_incremental.pdf', 'rb').read()
pos = 0; i = 1
while True:
    idx = d.find(b'%%EOF', pos)
    if idx == -1: break
    end = idx + 5
    open(f'version{i}.pdf', 'wb').write(d[:end])
    print(f'Version {i}: bytes 0-{end} saved')
    i += 1; pos = end
"

🔍 4. What to Examine in Each Prior Version

Extracting the version files is only the first step. The forensic value comes from comparing them systematically. Each version is an independent PDF and can be queried with all the same tools used on the current file.

a. Metadata Evolution

Each version carries its own /Info dictionary in its trailer. Running pdf> metadata or exiftool against each version file reveals how the metadata changed over time — which fields were added, removed, or altered in each save. This is one of the most revealing comparisons available to an examiner.

Compare metadata across all versions
exiftool version1.pdf version2.pdf version3.pdf

# Or in peepdf, open each version individually:
peepdf -i version1.pdf
pdf> metadata
pdf> exit

peepdf -i version2.pdf
pdf> metadata
pdf> exit
🔍
What the metadata evolution tells you

Comparing metadata across versions can reveal:

  • Producer changes — a different application name in V2 confirms a different tool made the edits. This is the most reliable indicator of who performed each editing session.
  • ModDate progression — the ModDate should advance with each version. If a later version has an earlier ModDate than a prior version, that field was backdated after the edit.
  • Creator disappearing — some editing tools strip the /Creator field on resave. Its absence in V2 but presence in V1 can help identify the editing application by what it removes.
  • New metadata fields appearing — fields like /Author or /Subject that appear only in later versions were added during editing, not at original creation.
  • XMP/Info divergence appearing — if V1 has matching Info and XMP but V2 does not, the editing tool updated one source but not the other — revealing which source carries the original values.

b. Content Changes Between Versions

Open each version in a PDF viewer and compare the visible content side by side. The difference between V1 and the current version is precisely what was altered. For documents involving contracts, invoices, or any claimed values, this visual comparison is the most direct proof of what changed and is directly presentable in proceedings.

For a more precise technical comparison, decode the content streams from corresponding pages across versions and diff them. New text blocks, new image placements, or new drawing operators that appear only in later versions are the fingerprints of each editing session.

Diff content streams across versions
# Decode the same page content stream from each version:
qpdf --show-object=CONTENTS_OBJ --filtered-stream-data version1.pdf > v1_page1.txt
qpdf --show-object=CONTENTS_OBJ --filtered-stream-data version2.pdf > v2_page1.txt

# Diff on Linux / macOS:
diff v1_page1.txt v2_page1.txt

# Diff on Windows (PowerShell):
Compare-Object (Get-Content v1_page1.txt) (Get-Content v2_page1.txt)

c. Annotation Timestamps and Authorship

Annotations added in later versions carry their own /CreationDate timestamps, set by the editing application at the moment the annotation is created. These are independent of the document-level ModDate and provide a second, often more reliable, timestamp for each edit event.

Cross-referencing the annotation /CreationDate with the version's ModDate provides corroboration: both should record approximately the same editing session. A significant gap between them may indicate one was manually altered after the fact.

The annotation /T field records the PDF editor's configured username at creation. Combined with the Producer field (which identifies the application), you have both the tool and the claimed operator identity for each editing event — a complete audit record of who did what and when.

d. Object-Level Changes

Each incremental update section (the bytes between successive %%EOF markers) contains its own xref table listing only the objects added or modified in that save. Reading these xref entries tells you exactly which object numbers the editing session touched, without having to read every object in the file. A session that modified only one or two objects — such as a salary figure — will show a correspondingly small xref table in the update section.

🔍
Reconstructing the full edit timeline

Combining all of the above produces a complete, version-by-version narrative:

  1. V1 — Original creation: Producer = authoring tool; CreationDate = document origin; content = original values; hash this version as a point-in-time integrity baseline
  2. V2 — First edit session: Producer changes to editing tool; ModDate advances; new objects added (annotations, overlays, replacements); annotation /CreationDate and /T record the session time and claimed operator identity
  3. V3 and beyond: apply the same analysis; isolate which objects each additional session modified and what content changed

Each version file can be independently hashed, giving you a verifiable integrity record for each historical state of the document — even though you are working from a single submitted file.

⚠️ 5. Limitations: What Incremental Updates Do Not Capture

Incremental updates record save events within a single file. They do not capture:

  • Pre-save manipulation — edits made in a tool that writes a fresh single-version file produce one %%EOF with no prior versions
  • Print-to-PDF re-creation — printing a manipulated PDF to a new PDF produces a clean single-version file; the original edit history is not transferred to the new file
  • Full-rewrite resaving — applications that save using "full rewrite" mode (rather than incremental update) replace the entire file on each save; qpdf and Adobe Acrobat both offer this mode. A suspicious document with only one %%EOF despite claimed edits may have been rewritten to erase its history
⚠️
Single %%EOF does not mean unedited

The absence of incremental update history means only that no incremental saves are recorded in the file as received. A document can be heavily manipulated and still show only one %%EOF if it was rewritten or recreated after the edits. Always investigate the other artifact categories — metadata anomalies, text overlay findings, image manipulation, EXIF discrepancies — regardless of the %%EOF count.
