Scenario

You have received a copy of an invoice. The subject claims the invoice total was always $48,500.00 and the due date was always 7 April 2025. Your task is to use incremental update analysis to determine the original values and establish when and how they were changed.

ℹ️
Before You Begin

Open a terminal in the folder containing lab03_incremental.pdf. You will be creating a new file (lab03_v1.pdf) during this lab. Keep notes with space for: EOF count, byte offsets of each EOF, V1 MD5, Producer for each version, and the original invoice total and due date.

🔬 Exercise 1 — Count %%EOF Markers and Find Their Byte Offsets

Goal: find out how many times this file has been saved, and where each save ends. A normal, once-saved PDF ends in a single %%EOF marker. Every time a compliant editor makes a change it appends the change and writes a new %%EOF — so counting the markers tells you how many saves the file has been through, and the earlier content is still physically present in the file.

ℹ️
Why this is the most important technique in document forensics

Because edits are appended rather than overwritten, a tampered PDF usually still contains, byte-for-byte, the version that existed before the edit. In Exercise 2 you will recover that original version and read what the document used to say. This exercise locates the save boundaries you need to do that.

Step 1 — Count the %%EOF markers

Count the markers with a one-line Python command (Python was installed in Module 00):

🪟 Windows
🐧 Linux / macOS
PowerShell
python -c "d=open('lab03_incremental.pdf','rb').read(); print(d.count(b'%%EOF'), 'EOF markers')"
Bash
python3 -c "d=open('lab03_incremental.pdf','rb').read(); print(d.count(b'%%EOF'), 'EOF markers')"
Terminal — counting %%EOF markers
python3 -c "d=open('lab03_incremental.pdf','rb').read(); print(d.count(b'%%EOF'), 'EOF markers')" 3 EOF markers

👆 3 markers. One is the original save; each additional marker is one incremental update. So 3 markers = 2 edits made after the document was first created.

Step 2 — Find the byte offset of each marker

Now locate exactly where each %%EOF sits. You need the first one’s position for Exercise 2.

🪟 Windows
🐧 Linux / macOS
PowerShell
python -c "import re; d=open('lab03_incremental.pdf','rb').read(); print([m.start() for m in re.finditer(b'%%EOF', d)])"
Bash
python3 -c "import re; d=open('lab03_incremental.pdf','rb').read(); print([m.start() for m in re.finditer(b'%%EOF', d)])"
Terminal — byte offsets of each %%EOF
python3 -c "import re; ... re.finditer(b'%%EOF', d) ..." [2698, 5582, 8759]

👆 The three markers start at bytes 2698, 5582, and 8759. The first marks the end of the original document — everything from byte 0 through that first %%EOF is the file as first saved. That is what you carve out in Exercise 2.

✅
What to record from Exercise 1

Q1 answer: 3 %%EOF markers = 2 incremental updates. Byte offsets: 2698, 5582, 8759. Carry the first offset (2698) into Exercise 2.

🔬 Exercise 2 — Extract Version 1 and Verify Its Contents

Goal: recover the original document. Copy every byte from the start of the file up to and including the first %%EOF into a new file. Because the first save is self-contained, that slice is a complete, valid PDF — the document exactly as it existed before any edits. This is the evidence that contradicts the inflated invoice.

Step 1 — Carve out Version 1

The first %%EOF starts at byte 2698 (Exercise 1); add 5 to include the five bytes of “%%EOF” itself, so copy bytes 0–2703:

🪟 Windows
🐧 Linux / macOS
PowerShell
python -c "d=open('lab03_incremental.pdf','rb').read(); e=d.find(b'%%EOF')+5; open('lab03_v1.pdf','wb').write(d[:e]); print('wrote', e, 'bytes')"
Bash
python3 -c "d=open('lab03_incremental.pdf','rb').read(); e=d.find(b'%%EOF')+5; open('lab03_v1.pdf','wb').write(d[:e]); print('wrote', e, 'bytes')"
Terminal — carving Version 1
python3 -c "...d.find(b'%%EOF')+5 ... open('lab03_v1.pdf','wb')..." wrote 2703 bytes

👆 You now have lab03_v1.pdf — 2703 bytes, the original document.

Step 2 — Confirm it is a valid PDF and hash it

qpdf + hash
qpdf --check lab03_v1.pdf
md5sum lab03_v1.pdf
Terminal — validating recovered Version 1
qpdf --check lab03_v1.pdf checking lab03_v1.pdf PDF Version: 1.7 No syntax or stream encoding errors found md5sum lab03_v1.pdf 038d8cd64cd74b4ced27f475fba5e108 lab03_v1.pdf

👆 It passes qpdf’s structural check — a clean, standalone PDF. Record its MD5; this identifies “the original version” as a distinct piece of evidence.

Step 3 — Open it and compare to the current file

Open lab03_v1.pdf in any viewer next to the original lab03_incremental.pdf:

FieldCurrent fileRecovered Version 1
Total Due$48,500.00$8,500.00
Due date18 July 202513 April 2025

👆 The recovered original says $8,500.00, due 13 April 2025; the current file shows $48,500.00, due 18 July 2025. You have recovered, from inside the suspect file itself, proof the total was inflated by $40,000 after creation.

✅
What to record from Exercise 2

Q2 answer: you copy bytes 0 through the end of the first %%EOF (2698 + 5 = 2703 bytes). Recovered Version 1 shows $8,500.00; record its MD5 (038d8cd64cd74b4ced27f475fba5e108).

🔬 Exercise 3 — Inspect the Modification Annotations

Goal: find out how the edit was done and when. The changes were made by laying FreeText annotations over the original numbers. Each annotation carries its own /CreationDate — a timestamp of the edit itself, separate from the document dates. You will list and read them.

Step 1 — Find the annotation objects

peepdf session
peepdf -i lab03_incremental.pdf
pdf> search /Annot
Terminal — pdf> search /Annot
pdf> search /Annot [17, 20]

👆 Two annotation objects: 17 and 20 — matching the two edits you counted in Exercise 1.

Step 2 — Read each annotation

Display each object and read its /Contents (the pasted text) and /CreationDate (when):

peepdf session
pdf> object 17
pdf> object 20
pdf> exit
Terminal — reading the two annotations
pdf> object 17 << /Type /Annot /Subtype /FreeText /Contents ($48,500.00) /CreationDate (D:20250618154703-07'00') /Rect [448 464 540 482] >> pdf> object 20 << /Type /Annot /Subtype /FreeText /Contents (Due: 18 July 2025) /CreationDate (D:20250702101500-07'00') /Rect [428 670 540 686] >>

👆 Object 17 pasted “$48,500.00” over the total on 18 June 2025; object 20 pasted “Due: 18 July 2025” on 2 July 2025. Both edit timestamps are months after the invoice’s own date (14 March 2025) and match the two incremental updates. You now know what changed, how, and exactly when.

✅
What to record from Exercise 3

Two FreeText annotations (objects 17 and 20) overlay the total and due date; their /CreationDate values (18 Jun 2025, 2 Jul 2025) date the tampering, well after the invoice date.

🔬 Exercise 4 — Compare Producer Fields Across Versions

Goal: show that a different tool touched the file after it was created. The original version was written by one application; the edits were written by another. Comparing the /Producer string in Version 1 against the current file reveals the handoff.

Step 1 — Producer of the recovered original (Version 1)

ExifTool on the recovered V1
exiftool -Producer -Creator lab03_v1.pdf
Terminal — Version 1 producer
exiftool -Producer -Creator lab03_v1.pdf Producer : LibreOffice 7.3 Creator : Writer

Step 2 — Producer of the current (edited) file

ExifTool on the current file
exiftool -Producer -Creator lab03_incremental.pdf
Terminal — current-file producer
exiftool -Producer -Creator lab03_incremental.pdf Producer : PDF-XChange Editor 10.0 Creator : Writer

👆 The original was produced by LibreOffice 7.3; the current file reports PDF-XChange Editor 10.0. The authoring tool (Creator = Writer) is unchanged, but the Producer changed — a classic “created in one program, edited in another” fingerprint. Both strings coexist in the raw bytes, because the original is still embedded:

both producers in the raw file
grep -a -o "/Producer ([^)]*)" lab03_incremental.pdf
Terminal — both producers present
grep -a -o "/Producer ([^)]*)" lab03_incremental.pdf /Producer (LibreOffice 7.3) <- revision 1 (original) /Producer (PDF-XChange Editor 10.0) <- the edits
✅
What to record from Exercise 4

Q4 answer: Version 1’s Producer is LibreOffice 7.3; the current file’s is PDF-XChange Editor 10.0. The change indicates the file was created in one application and later edited in a different, dedicated PDF editor — corroborating the incremental-update and annotation findings.

📝 Knowledge Check Preparation

Q1: A PDF file contains 3 %%EOF markers. How many incremental updates does this indicate?

2 incremental updates.

The first %%EOF marks the end of the original save. Each additional %%EOF is one appended edit. So the count of updates is always (number of %%EOF markers) − 1 — here, 3 − 1 = 2. This file was created once and then edited twice.

Why it matters: every extra marker is a save that left the previous version intact inside the file. Two updates means there are potentially two earlier states you can recover and read.

Q2: When extracting Version 1, what bytes do you copy?

Bytes 0 through the end of the first %%EOF marker — here, 2703 bytes (offset 2698 + 5).

The first %%EOF starts at byte 2698 (from Exercise 1). The marker itself is five characters (%%EOF), so you include up to byte 2698 + 5 = 2703. That slice — d[:2703] — is the complete original document, because the first save wrote a self-contained PDF ending in that marker.

Tip: use d.find(b'%%EOF')+5 rather than typing the number, so the same command works on any file regardless of where its first marker falls.

Q3: What does the /Prev entry in an incremental update trailer do?

It points to the byte offset of the previous cross-reference section — the link that chains one saved version back to the one before it.

Each incremental update appends its own small cross-reference table listing just the objects it changed, and its trailer carries a /Prev entry giving the file offset of the previous cross-reference section. Following the /Prev chain is how a PDF reader (and an examiner) walks backwards through the save history. In this file you can see the chain with grep -a "/Prev" lab03_incremental.pdf, which returns the offsets 2251 and 5290 — two /Prev pointers for the two updates.

Why it matters: the presence of /Prev is itself a reliable signal that the file was modified by incremental update, and each pointer marks another recoverable earlier state.

Q4: V1 Producer is 'LibreOffice 7.3' and V2 Producer is 'PDF-XChange Editor 10.0'. What does this indicate?

The document was created in one application and later edited in a different one — evidence of post-creation modification.

The original version (V1) was produced by LibreOffice 7.3. The current file reports PDF-XChange Editor 10.0 as its Producer, while the Creator (the authoring application) is still “Writer.” That pattern — same Creator, changed Producer — is the classic fingerprint of a file that was authored in an office suite and then opened and altered in a dedicated PDF editor.

Because the original is still embedded, both Producer strings are present in the raw bytes at once (grep -a "/Producer" lab03_incremental.pdf shows both). Taken with the recovered $8,500 original (Exercise 2) and the dated FreeText annotations (Exercise 3), this completes the picture: created in LibreOffice in March, then edited in PDF-XChange in June and July to inflate the total.
